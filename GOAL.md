# Техническое задание: Upscayl Mobile

**Рабочее название:** Upscayl Mobile  
**Файл:** `goal.md`  
**Платформа:** Android  
**Тип:** Open Source, полностью локальная обработка изображений.

## 1. Цель проекта

Разработать Android-приложение для увеличения разрешения изображений с помощью нейросетей.

Основные требования:
- Полностью автономная работа без интернета.
- Обработка изображений непосредственно на устройстве.
- Использование Real-ESRGAN и NCNN с аппаратным ускорением через Vulkan, когда оно доступно.
- Простой, современный интерфейс.
- Отсутствие регистрации, рекламы, подписок и телеметрии.
- Возможность установки через APK.
- Открытый исходный код.

Приложение должно работать на современных Android-смартфонах, включая устройства со Snapdragon и MediaTek.

**Главный принцип:** пользователь выбирает изображение, нажимает одну кнопку и получает улучшенный результат.

| Тестирование | JUnit, Android instrumentation tests | Проверка логики и устройств |

### Важное техническое решение

Необходимо изучить исходный код и лицензию движка Upscayl/NCNN до начала интеграции.

Рекомендуемый подход:
1. Исследовать репозиторий NCNN-реализации Upscayl.
2. Проверить возможность сборки движка для Android ARM64.
3. Проверить Vulkan-совместимость и необходимые зависимости.
4. Создать JNI-обёртку между Kotlin и C++.
5. Реализовать загрузку моделей и обработку изображений.
6. Подключить движок к пользовательскому интерфейсу.

Не следует переписывать вычислительное ядро на Kotlin или заменять его другой библиотекой без необходимости.

**Критически важно:** наличие Vulkan на устройстве не гарантирует, что конкретная сборка NCNN или модель будет работать на нём. Нужны проверка поддержки и резервный сценарий.

### Сценарий работы

1. Пользователь открывает приложение.
2. Выбирает изображение из галереи.
3. Видит превью и разрешение исходника.
4. Выбирает модель и масштаб.
5. Нажимает «Улучшить».
6. Видит ход обработки.
7. Получает результат.
8. Сравнивает оригинал и обработанное изображение.
9. Сохраняет результат или делится им.

### UX-принципы

- Не спрашивать разрешение на доступ ко всей галерее, если достаточно системного выбора фотографий.
- Не заставлять пользователя разбираться в технических параметрах модели.
- Показывать понятные ошибки, а не коды исключений.
- Сохранять настройки между запусками.
- Не терять исходник при обработке.
- Не блокировать интерфейс во время вычислений.

## 4. Нейросетевые модели

Для первой версии достаточно одной проверенной модели.

| Модель | Назначение | Приоритет |
|---|---|---|
| Real-ESRGAN x4plus | Универсальный апскейл фотографий | P0 |
| Real-ESRGAN x4plus-anime | Аниме и иллюстрации | P1 |
| Другие совместимые модели | Расширение возможностей | P2 |

Модели необходимо хранить отдельно от исполняемого кода, если это допускают выбранная архитектура и требования к распространению.

Возможные варианты:
- включить базовую модель в APK;
- поставлять её отдельным файлом;
- предусмотреть импорт совместимых моделей пользователем.

Для MVP я рекомендую **встроенную базовую модель**, чтобы после установки приложение сразу было готово к работе офлайн.

Перед включением каждой модели нужно проверить лицензию, формат весов и совместимость с выбранной версией NCNN.

## 5. Движок обработки изображений

Это наиболее сложная часть проекта.

### Требования

Реализовать нативный модуль C++ с JNI-интерфейсом для вызова из Kotlin.

Он должен уметь:
- инициализировать NCNN;
- загружать модель;
- принимать изображение;
- выполнять нейросетевой апскейл;
- возвращать обработанное изображение;
- сообщать об ошибках;
- освобождать ресурсы GPU и CPU;
- корректно обрабатывать отмену задачи, если это поддерживается архитектурой.

### Конфигурация вычислений

Приоритет:
1. Vulkan на совместимом GPU.
2. CPU как резервный вариант, если соответствующая сборка поддерживает выполнение модели на CPU.
3. Понятное сообщение пользователю, если ни один вариант не работает.

Не нужно автоматически считать CPU-режим полноценной заменой GPU: производительность может отличаться на порядок.

### Обработка больших изображений

Апскейл в четыре раза увеличивает ширину и высоту изображения, то есть число выходных пикселей возрастает в 16 раз.

Поэтому необходимо:
- оценивать размер изображения до запуска;
- контролировать использование памяти;
- избегать лишнего копирования больших буферов;
- предусмотреть обработку тайлами, если она совместима с моделью;
- проверять качество на стыках тайлов;
- корректно обрабатывать ошибки нехватки памяти.

Например, изображение размером 4000 × 3000 пикселей после увеличения в четыре раза станет 16000 × 12000, то есть 192 мегапикселя.

Такой результат требует аккуратной работы с памятью даже на мощном смартфоне.

**Тайловая обработка должна быть частью технического плана, а не необязательной оптимизацией после появления проблем.**

## 7. Сохранение изображений

Поддерживаемые форматы:
- PNG;
- JPEG.

Для MVP достаточно этих двух форматов.

Требования:
- сохранение в системную галерею;
- понятное имя файла;
- отсутствие перезаписи оригинала;
- отображение уведомления об успешном сохранении;
- корректная работа с EXIF, если метаданные сохраняются;
- отсутствие неожиданных потерь качества при экспорте.

При сохранении JPEG пользователь должен иметь возможность выбрать качество. Для PNG настройка качества не требуется.

## 8. Производительность и совместимость

### Целевые устройства

- Android 12 и новее.
- ARM64.
- Смартфоны с Qualcomm Snapdragon.
- Смартфоны с MediaTek Dimensity.
- Устройства с поддержкой Vulkan.
- Устройства без пригодного Vulkan-пути, если они поддерживаются CPU-режимом.

Минимальная версия Android здесь предварительная: окончательно её следует определить после проверки зависимостей, сборки NCNN и выбранных API.

### Требования к стабильности

- Приложение не должно зависать из-за длительных вычислений.
- Должно корректно переживать отмену обработки.
- Не должно аварийно завершаться при нехватке памяти без попытки сообщить пользователю об ошибке.
- Не должно терять исходное изображение.
- Не должно отправлять изображения на сервер.
- Должно корректно работать при сворачивании приложения, насколько это позволяет выбранная схема фоновой обработки.

### Диагностика

В разделе «О приложении» можно показывать:
- модель устройства;
- версию Android;
- доступность Vulkan;
- выбранный вычислительный режим;
- версию движка;
- доступную информацию о модели.

Это поможет разбираться с проблемами на разных устройствах.

## 11. Критерии приёмки MVP

Версия считается готовой, если:

1. Проект собирается в APK без ручного изменения исходников.
2. Приложение устанавливается на ARM64-устройство.
3. Изображение выбирается через системный интерфейс Android.
4. Реальная нейросетевая модель выполняет апскейл.
5. Результат визуально соответствует ожидаемому увеличению разрешения.
6. Поддерживается локальная обработка без сети.
7. Результат сохраняется в галерею.
8. Приложение не падает при ошибках загрузки модели.
9. Проверена работа на нескольких изображениях разного размера.
10. В репозитории есть инструкции по сборке.
11. Указаны лицензии приложения, движка и моделей.
12. В README перечислены известные ограничения.

Для первой версии не нужны аккаунты, облачные вычисления, подписки, встроенный редактор изображений или сложная система истории.

# Три решения, которые я бы принял заранее

**1. Не портировать Electron.** Нативный Kotlin + Compose для интерфейса и C++/NCNN для обработки дадут более естественное Android-приложение.

**2. Сначала доказать работоспособность движка.** Главный риск проекта — не интерфейс, а сборка и стабильная работа нейросетевого движка на Android. Поэтому первый результат должен быть техническим прототипом, а не макетом экранов.

**3. Сделать приложение независимым от конкретного производителя смартфона.** Vulkan использовать при наличии совместимого пути, а CPU предусмотреть как резерв. При этом честно сообщать о возможностях и ограничениях устройства.
