## Боль и цель

Боль: мощный Android-планшет или телефон простаивает, а ИИ-агент на компьютере (Claude Code, Codex и другие) не может
отдать ему задание на апскейл без человека у экрана. Цель (Achieve): агент на компьютере отправляет изображение на
устройство с KARTUN, получает увеличенный результат и отчёт о прогоне — по кабелю через ADB или по локальной сети Wi-Fi
через HTTPS — без касания экрана.

## Критерии приёмки

1. **ADB.** Команда на компьютере `kartun upscale photo.jpg --model fast --scale 4` (обёртка над `adb`) кладёт
   изображение на устройство, запускает задание и забирает результат; в консоль печатается одна JSON-строка
   (размеры, модель, GPU или CPU, время). Проверка: прогон на Титане, результат 4× по размеру.
2. **Локальная сеть.** Агент делает `POST https://<ip-устройства>:<порт>/v1/upscale` с ключом доступа и картинкой и
   получает результат. Без ключа — отказ `401`. Сервер включается в настройках и видит только локальную сеть.
3. **Описание для агентов.** В репозитории есть короткий документ API (команды, поля JSON, коды ошибок), по которому
   агент без человека проходит пункты 1 и 2.
4. **Офлайн-обработка сохраняется:** изображение не уходит дальше устройства, которому его прислали.

## Что уже есть

Проба фазы 0 (`app/.../MainActivity.kt`, `tools/titan-probe.mjs`) — зародыш режима ADB: задание передаётся
`adb shell am start … --es in <файл> --es model <модель> --ez gpu true --ei tile 200`, результат — JSON-строка в
logcat с тегом `KARTUN_PROBE`. Этот режим работает без разрешения сети.

## Предлагаемый путь (`[AI]`, требует плана фазы)

1. Фаза 4: режим ADB — стабильный контракт команд (intent или `adb shell content call`), CLI-обёртка `tools/kartun-cli`
   для компьютера, документ API.
2. Фаза 5: HTTPS-сервер в локальной сети — самоподписанный сертификат с отпечатком на экране устройства, ключ доступа,
   очередь заданий в службе `mediaProcessing`, которая обрабатывает фото из интерфейса.
